# First Development Flow

首次开发主循环适用于目标已经相对明确、但项目还没有该能力的正式规格和实现。
它负责把讨论稿逐步变成可实现、可验收、可作为版本基线的项目资料。

## 阶段表

| 阶段 | 输入 | 主要工作 | 产出 |
| --- | --- | --- | --- |
| 需求讨论 | 用户想法、项目背景、已有约束 | 必要时按 Grill Me 逐题澄清目标、用户、范围、非目标和成功标准 | 可编写简报的结论 |
| 需求简报 | 讨论结论、项目资料 | 在同一份文档中整理问题、目标、范围、非目标和成功标准 | `brief.md` |
| SPEC | `brief.md`、项目宪章、背景资料 | 把目标转成用户场景、可验证需求、边界和验收条件；在同一份文件中修订 | 完整 `spec.md` |
| Plan | 完整 `spec.md`、技术约束、源码结构、必要研究 | 形成架构、数据、接口、模块职责、迁移和验证设计 | 完整 `plan.md` |
| Tasks | 完整 `spec.md`、`plan.md`、源码和测试 | 仅在复杂度值得拆分时，生成有依赖关系的执行任务 | `tasks.md`（按需） |
| Implement | 完整目标 SPEC、完整目标 Plan、Tasks（如有） | 实现、生成或补充测试、运行针对性测试和回归 | 源码、测试、实施记录 |
| 验收 | 实现结果、测试证据、用户需要确认的事项 | 核对规格和验收条件，区分 Agent 证据与用户确认 | `acceptance.md`、`implementation-report.md` |
| 基线 | 验收结论、发布范围 | 固化当前完整 Spec、Plan、代码和测试的对应关系 | `releases.md` 中的版本记录 |

## 推进规则

1. 文档阶段可以往返，但不重复创建同类文档。需求变化回到 Brief 或 SPEC，技术方案
   变化回到 Plan，执行拆分变化回到 Tasks。
2. Plan 前必须检查技术未知项；如果未知项会改变架构、数据或核心依赖，先做必要研究
   或小型验证，再把结论写入 Plan。
3. Implement 前检查需求覆盖：每个重要需求都应能在 Plan、Tasks（如有）、测试或验收
   记录中找到对应关系。
4. 测试失败时先分类：实现错误回到实现，技术方案错误回到 Plan，产品行为错误回到
   SPEC，目标尚不清楚回到 Brief 或访谈。
5. 验收通过后才把当前完整文档、代码和测试视为同一个版本基线；未通过的问题进入
   变更评估或 BugFix 小循环。

## 进入条件与结束条件

- 进入条件：用户目标足够清楚，或者访谈已经达到停止条件；项目目录和既有约束已查明。
- 阶段结束：本阶段产物已形成，关键歧义已经解决或明确记录为假设/待确认事项。
- 主循环结束：实现完成，客观测试有证据，必要的人工测试已得到反馈，版本基线资料一致。
