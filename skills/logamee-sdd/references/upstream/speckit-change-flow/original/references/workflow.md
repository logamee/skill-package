# Change Flow Workflow

## 1. 绑定当前项目

从调用时的工作目录开始：

1. 运行 `git rev-parse --show-toplevel`。成功时以返回值为项目根目录。
2. 不是 Git 项目时，以当前目录为边界，并确认其中存在可识别的源码或项目配置。
3. 检查 `.specify/`、`specs/`、测试目录、构建配置和项目说明。
4. 后续读写限制在当前项目内，除非用户明确指定其他位置。

不要根据历史对话自动切换到另一个同名项目。

## 2. 整理输入

用户可以提供口头描述、测试记录、日志、截图或多个问题。先整理：

- 触发条件；
- 复现步骤；
- 期望结果；
- 实际结果；
- 影响范围；
- 已知环境；
- 尚未确认的信息；
- 是否包含新的用户目标。

一次输入包含多个独立问题时，分别登记。只有根因和交付范围必须一起完成时，才在
混合版本中绑定它们。

## 3. 记录来源

### 只有实现问题

优先写入：

```text
specs/<feature>/acceptance-issues.md
specs/<feature>/bugs/<issue-id-lower>-<short-slug>/assessment.md
```

### 只有新增需求

写入项目约定的：

```text
product-backlog.md
```

沿用已有编号和字段。如果没有编号规则，使用 `PB-001` 形式。初始状态通常为
`Inbox`。

### Bug 与新增需求同时出现

分别写入 Issue 和 Product Backlog，并互相引用：

```text
Issue → 关联 PB 编号
PB → 触发 Issue 编号
```

不要把新增需求塞进 Bug 的修复范围，也不要把 Bug 的失败事实改写成需求描述。

## 4. Assess：判断来源与模式

阅读相关 SPEC、Plan、验收条件、代码和测试后，判断：

| 判断 | 含义 | 入口 |
| --- | --- | --- |
| 实现缺陷 | 已有要求正确，实现没有满足 | BugFix 小循环 |
| Plan 调整 | 目标不变，但技术方案或职责需要改变 | Plan |
| SPEC 调整 | 既有产品目标的正式要求需要修正 | SPEC |
| 新增需求 | 当前没有承诺的新产品目标 | Product Backlog |
| 混合版本 | Issue 与新增需求决定一起交付 | 版本 Proposal |

Plan 或 SPEC 调整不自动等于新增需求。如果只是修正已有目标，不建立 PB；如果
调整中产生了新的用户目标，则额外建立 PB。

## 5. 人工门禁一：确认模式

在修改代码、SPEC、Plan、Tasks 或版本文件前暂停，向用户报告：

```text
本次反馈：
已有 Issue：
新增 PB：
Assess 结论：
建议模式：
建议入口：
建议版本：
预计修改范围：
不会修改：
```

必须得到用户明确确认。用户改变模式或范围时，先更新 Assess，再继续。

## 6. 执行模式一：单独 BugFix

1. 根据 `assessment.md` 增加能够稳定复现问题的失败测试。
2. 运行测试，确认失败原因与问题一致。
3. 做满足已有要求的最小修复。
4. 不修改 SPEC、Plan 或 Product Backlog。
5. 运行针对性测试和合理范围的回归测试。
6. 写入 `fix.md` 和 `test.md`。
7. 自动化测试通过后标记 `Fixed`。
8. Agent 执行客观验收；验收条件已覆盖且通过时标记 `Verified` 并关闭 Issue。原始输入只有在包含自动化/代表性测试未覆盖的独特条件时才需要重跑，不为形式重复测试。

测试无法自动化时，在 `fix.md` 和 `test.md` 记录原因及替代验证。

## 7. 执行模式二：单独新增需求

1. 完善 PB 的问题、目标、范围和进入 SPEC 的条件。
2. 用户确认后，将 PB 改为 `Ready for Spec`。
3. 如需版本范围管理，建立或更新 Proposal。
4. 调用 `$speckit-specify`。
5. 调用 `$speckit-plan`、`$speckit-tasks` 和 `$speckit-implement`。
6. 按 SPEC 的验收条件测试。
7. 将 PB 更新为对应版本或完成状态。

不要为了一个已经清楚的小需求强行编写独立需求简报。

## 8. 执行模式三：混合版本

1. 保留原 Issue 和 PB，不建立第二份同义记录。
2. 在 Proposal 中明确接纳哪些 Issue 和 PB。
3. 将 Bug 的验收要求和新需求一起写入版本 SPEC。
4. 用同一份 Plan、Tasks 和 Implement 完成版本。
5. 用版本测试回测原始 Bug 场景，并测试新增需求。
6. 在 Issue 中回写版本、测试结果和当前状态。
7. 在 PB 中回写接纳版本和交付结果。
8. 按“Agent 收尾”和“用户收尾”分工。Agent 收尾的问题通过客观测试后由 Agent 关闭；
   用户收尾的问题即使完成了技术预检，也保持开放并交给用户验收。

混合版本不再单独执行 BugFix 小循环，否则会产生两套相互竞争的实现计划。

## 9. 验收责任与关闭

完成验证后报告：

- 实际修改的文件；
- 执行过的测试及结果；
- 没有执行的测试及原因；
- 原始场景复测结果；
- Issue、PB 和版本文件当前状态；
- 未完成事项和风险。

Agent 收尾的问题必须满足：输入、规则、预期结果和允许误差都可以事先写清楚，不同
的人重复测试应得到相同结论。例如数值范围、枚举值、Schema、状态流转、数据完整性
和链接存在性。达到验收条件后，Agent 直接标记 `Verified` 并关闭，不再让用户重复
执行同一测试。

以下情况统一归入用户收尾：

- 是否保留了原文的实际用途、关键步骤和必要信息；
- 内容提炼、表达方式或页面组织是否符合用户偏好；
- UI、布局、间距、字号、颜色和视觉风格；
- Markdown/HTML 是否最终呈现为用户可读、语义合理的结构；
- 交互流程是否自然、清晰且符合使用习惯；
- 需要用户权限、真实业务判断或 Agent 当前无法取得的材料才能确认。

Agent 可以验证这些问题的技术基础，例如节点是否生成、标签是否存在、按钮是否能
触发，但这只是技术预检，不改变收尾责任。此类 Issue 必须说明“用户测什么、怎样
算通过”，并保持未关闭；用户不需要重复执行已经完成的技术预检。

## 10. 完成条件

一次处理完成时，以下信息必须一致：

- Issue 或 PB 中的编号、分类和状态；
- `assessment.md` 的路径判断；
- `fix.md` / `test.md` 或版本级 Plan、Tasks、测试记录；
- Git 工作区中的实际修改；
- 验收条件对应的测试证据，以及原始场景未重跑时的理由。
