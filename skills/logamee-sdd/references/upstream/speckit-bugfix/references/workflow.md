# Bugfix Workflow

## 1. 绑定当前项目

从调用时的工作目录开始：

1. 运行 `git rev-parse --show-toplevel`。成功时以返回值为项目根目录。
2. 不是 Git 项目时，以当前目录为边界，并确认其中存在可识别的源码或项目配置。
3. 检查 `.specify/`、`specs/`、测试目录、构建配置和项目说明。
4. 后续读写都限制在该项目内，除非用户明确指定其他位置。

不要根据历史对话自动切换到另一个同名项目。

## 2. 整理原始问题

用户可以提供口头描述、测试记录、日志、截图或多个问题。Agent 负责整理：

- 触发条件；
- 复现步骤；
- 期望结果；
- 实际结果；
- 影响范围；
- 已知环境；
- 尚未确认的信息。

一次输入包含多个独立问题时，分别登记。只有根因和修复必须一起完成时，才把
它们合并，并在记录中说明理由。

可以执行普通只读检查和本地复现。涉及外部写入、生产环境、账号授权、付费服务
或不可逆操作时，执行前单独征求确认。

## 3. 定位功能与问题总表

按以下顺序定位问题所属功能：

1. 用户明确指定的 feature 或 SPEC；
2. 问题中提到的需求编号、验收记录或源码范围；
3. 当前分支和 `specs/` 中唯一匹配的功能；
4. 项目只有一个活动功能时使用该功能。

存在多个合理候选时，询问用户，不要自行选择。

优先使用：

```text
specs/<feature>/acceptance-issues.md
```

如果功能明确但问题总表不存在，可以建立最小问题总表。沿用项目已有编号前缀；
例如已有 `AI-001`、`AI-002` 时，下一个编号为 `AI-003`。项目没有编号规则时，
使用 `BUG-001`。

新增条目的初始状态为 `Open`。至少记录编号、日期、状态、现象、期望结果、
复现条件和验收条件。日期使用执行当天的本地日期。

## 4. 建立问题目录

新问题默认创建：

```text
specs/<feature>/bugs/<issue-id-lower>-<short-slug>/
└── assessment.md
```

Slug 使用稳定、简短的英文问题描述。

如果问题总表已经指向现有目录，则继续使用该目录。发现旧记录位于
`.specify/bugs/` 时，不要静默移动或复制；继续处理现有问题，并单独提示这是
旧目录约定。迁移会影响软链接或引用，必须得到用户授权。

## 5. Assess

在修改代码前完成以下工作：

1. 尽量复现问题，保存命令、输入和实际输出。
2. 阅读相关 SPEC、Plan、验收条件、代码和测试。
3. 查找最接近根因的证据，不根据报错文本直接下结论。
4. 判断问题属于哪一层：

| 分类 | 判断标准 | 建议入口 |
| --- | --- | --- |
| 实现缺陷 | 已有 SPEC 和 Plan 正确，实现没有满足它们 | Bugfix 小循环 |
| Plan 调整 | 预期行为不变，但技术方案、数据结构或模块职责需要改变 | Plan |
| SPEC 调整 | 真实测试证明系统预期行为本身需要改变 | SPEC |
| 新目标 | 处理范围增加了新的用户目标或独立能力 | Proposal |

把证据和建议写入 `assessment.md`。此阶段不得修改源码、测试、SPEC 或 Plan。

## 6. 人工门禁一：确认处理路径

向用户给出简明报告，不要只丢出文件路径：

```text
问题：AI-003
判断：实现缺陷
原因：……
建议：进入 Bugfix 小循环
范围：预计修改……
不会修改：SPEC、Plan……
```

然后明确询问是否按建议路径继续。没有得到确认时停止。

如果用户修改了分类或范围，先更新 `assessment.md`，再进入获批路径。

## 7. 执行获批路径

### 实现缺陷

1. 根据 `assessment.md` 增加能够稳定复现问题的失败测试。
2. 运行测试，确认失败原因与问题一致。
3. 做满足已有要求的最小修复。
4. 避免无关重构，不修改 SPEC 和 Plan。
5. 运行针对性测试和合理范围的回归测试。
6. 写入 `fix.md` 和 `test.md`。
7. 修复完成且自动化测试通过后，将问题状态更新为 `Fixed`。

测试先行不适用时，例如问题只能依赖外部系统人工复现，应在 `fix.md` 中记录
原因，并建立能够覆盖最低风险边界的替代验证。

### Plan、SPEC 或新目标

本 Skill 保留 Issue 和 Assess 记录，但不伪装成小循环继续修改代码。

- Plan 调整：从现有 SPEC 出发修改 Plan，并重新生成或更新 Tasks。
- SPEC 调整：先修改 SPEC，再检查 Plan、Tasks 和实现。
- 新目标：按项目约定建立 Proposal，再进入 SPEC、Plan、Tasks 和 Implement。

优先调用当前项目已经安装的 Spec Kit skills。调用前说明即将进入的阶段和预计
产物；不得跳过用户已经要求的人工审核节点。

## 8. Test 与状态

验证至少分为：

1. 针对性测试：证明原问题被覆盖。
2. 回归测试：证明相关功能没有明显退化。
3. 原始场景复测：使用最初失败的输入和环境重新执行。

状态含义：

| 状态 | 使用条件 |
| --- | --- |
| Open | 已登记，尚未完成路径判断 |
| Clarifying | 缺少需求或环境信息 |
| Ready | 路径和范围已经由用户确认 |
| Fixed | 修复完成，相关自动化测试通过 |
| Verified | 原始失败场景已经重新验证通过 |
| Closed | 用户明确同意关闭，或明确决定不处理 |

外部授权失效、测试环境不可用或原始数据缺失时，保持 `Fixed`，不要写成
`Verified`。

## 9. 人工门禁二：确认关闭

在修改为 `Closed` 前，向用户报告：

- Fix 的实际文件范围；
- 测试命令和结果；
- 原始场景复测结果；
- 当前状态以及为什么；
- 未完成事项。

询问用户是否关闭。用户可以选择：

- 保持 `Fixed`，以后继续复测；
- 标记 `Verified`，暂不关闭；
- 确认 `Closed`；
- 重新打开并补充修复。

得到确认后再更新问题总表和变更记录。

## 10. 完成条件

一次处理完成时，以下信息必须一致：

- 问题总表中的编号、分类和状态；
- `assessment.md` 的范围判断；
- `fix.md` 的实际修改；
- `test.md` 的真实测试结果；
- Git 工作区中的代码和测试。

不要因为用户暂时离开或环境阻塞而自动关闭问题。
