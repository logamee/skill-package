# Bootstrap Mode Protocol

Bootstrap 模式用于项目尚未形成稳定 V1 基线的阶段。此时需求、架构、模块边界和实现
都可能快速变化，不能要求每个反馈都先生成正式 SPEC、Change、完整 Plan 和 Tasks。

Bootstrap 模式减少的是文档和流程负担，不是测试责任。AI 仍然要主动测试，并保留足够
的问题记忆，避免快速开发变成不可追踪的反复修改。

## 进入条件

满足下列情况之一时，可以使用 Bootstrap 模式：

- V1.0 尚未形成；
- 核心架构或模块边界仍在探索；
- 用户目标还会随运行结果快速调整；
- 当前项目还没有可以作为判断依据的稳定 SPEC 和版本基线。

已有稳定 V1 基线后，不应继续把普通功能变更长期留在 Bootstrap 模式；应切换到首次开发
主循环或变更评估模式。

## 最小资料

Bootstrap 模式只维护三份资料：

```text
sdd/bootstrap/
├── bootstrap-spec.md
├── plan.md
└── issues.md
```

- `bootstrap-spec.md`：Bootstrap 阶段的轻量需求与产品行为规格，由用户与 AI 共同完善。
- `plan.md`：轻量技术实现计划，记录当前采用的实现方向；不要求达到正式 SDD Plan
  的完整性，可以随着开发结果持续重写。
- `issues.md`：测试过程中发现的问题台账。

不建立正式 SPEC、Tasks、Change Spec 或独立的测试报告。Bootstrap 的 `plan.md` 是
轻量技术计划，不等同于正式版本 Plan。普通自测结果直接由 AI 在当前工作过程中报告；
与问题相关的测试证据写入对应的 `issues.md` 条目。

## 开发与测试循环

```text
bootstrap-spec.md 中的当前目标
  ↓
用户与 AI 共同完善 bootstrap-spec.md
  ↓
AI 根据 bootstrap-spec.md 和 plan.md 开发
  ↓
AI 生成测试示例并尽可能执行
  ↓
发现问题则生成 AI 编号并写入 issues.md
  ↓
需要人工判断的部分 → 提交人工测试清单 → 用户反馈
  ↓
更新 issues.md 状态
  ↓
修复、复测原问题、回归受影响功能
  ↓
将确认后的行为回写 bootstrap-spec.md；技术方案变化回写 plan.md
  ↓
继续开发
```

## AI 自测要求

每次完成一段功能后，AI 应主动：

1. 从当前目标、已有行为和代码结构中推导测试场景；
2. 优先生成并执行自动化测试；
3. 至少覆盖正常路径、边界条件、错误处理和与修改区域相关的回归路径；
4. 对发现的问题记录实际执行的命令、输入、预期结果、实际结果和未执行项目；
5. 失败时先判断是代码问题、目标变化还是环境限制，再决定修复或向用户提问；
6. 修复后重新执行原失败场景，不得只报告“代码已经修改”；
7. 确认后的行为变化回写 `bootstrap-spec.md`；技术方案变化回写 `plan.md`，让开发资料与当前
   实现保持一致。

Bootstrap 阶段没有正式验收场景时，AI 生成的场景是“临时验证场景”，不是正式 SPEC。
它们用于帮助发现问题，不能被伪装成用户已经确认的产品要求。

## 人工测试要求

以下情况应交给用户人工测试：

- 视觉布局、文案、内容取舍；
- 交互是否自然、是否符合使用习惯；
- 需要真实账号、真实设备、真实外部环境或真实业务判断；
- AI 无法取得的主观验收材料。

提交给用户的人工测试请求必须包含：

```text
测试目的
测试前置条件
操作步骤
需要观察的结果
通过标准
反馈格式
```

用户反馈后，AI 负责把反馈转换为问题条目，不要求用户自己整理成 Issue。

## `bootstrap-spec.md` 的使用方式

`bootstrap-spec.md` 可以从一段非常随意的讨论稿开始，不要求固定模板。用户和 AI 在开发前、
开发中共同完善它，直到内容足够描述当前要开发什么。

建议逐步收敛出以下内容，但不要求一次写齐：

```markdown
# Bootstrap 工作规格

## 当前目标

## 已确认的功能

## 当前要解决的问题

## 暂时不做

## 重要约束

## 待确认事项

## 已确认的行为修正
```

它不是正式规格，也不要求满足 SPEC 的完整性标准。它的唯一要求是：

- 用户和 AI 能理解当前要开发什么；
- AI 能据此判断产品目标和行为；
- 发现问题并确认后，文档能被及时修正；
- 文档描述的是当前有效目标，而不是已经过时的想法。

`bootstrap-spec.md` 主要描述“做什么”，不要把具体框架、模块、数据表或接口实现细节作为主要
内容写入其中。技术实现放入下面的 `plan.md`。

## `plan.md` 的使用方式

Bootstrap 的 `plan.md` 是当前的轻量技术计划，不是正式 SDD Plan，也不是不可变的设计
承诺。它至少可以逐步记录：

```markdown
# Bootstrap 技术计划

## 当前实现目标

## 当前架构和模块

## 数据与接口

## 实现顺序

## 测试策略

## 技术限制与待验证事项
```

`plan.md` 主要描述“怎么做”。当技术方案、模块职责、数据结构、接口或实现顺序发生变化
时更新它；不要因为每次代码修改都机械地重写计划。代码问题应先记录到 `issues.md`，
只有确认技术方案变化时才同步修改 `plan.md`。

## 轻量问题台账

Bootstrap 模式从第一天就记录问题，但不建立完整的 Issue、Backlog、Proposal 体系。
所有问题统一写入 `issues.md`。沿用项目已有的问题编号规范；项目没有编号规范时，默认
使用 `AI-001`、`AI-002` 的连续编号。

每个问题至少包含：

```markdown
## AI-001：问题标题

| 字段 | 内容 |
| --- | --- |
| 编号 | AI-001 |
| 状态 | 待解决 |
| 发现方式 | AI 自测 / 人工测试 |
| 严重程度 | 阻塞 / 高 / 中 / 低 |
| 关联 Bootstrap Spec | `bootstrap-spec.md` 中的功能或段落 |

### 复现步骤

### 期望结果

### 实际结果

### 修复记录

### 验证记录

### 回写 Bootstrap Spec
```

## 问题状态

推荐使用以下轻量状态：

| 状态 | 含义 |
| --- | --- |
| `待解决` | 已记录，尚未处理 |
| `处理中` | 正在分析或修复 |
| `待人工测试` | AI 已修复，需要用户测试 |
| `已解决` | AI 或用户确认问题已解决 |
| `暂不处理` | 当前阶段明确延期 |
| `重新打开` | 复测失败或问题再次出现 |

“已解决”必须有验证记录。只要涉及视觉、交互、真实环境或主观判断，就必须先进入
“待人工测试”，用户反馈通过后才能标记“已解决”。

## 问题处理循环

每个问题都按照下面的轻量循环处理：

```text
AI-001：待解决
  ↓
分析并修复
  ↓
AI 自测
  ↓
需要人工测试？──是──→ 待人工测试 → 用户反馈
  │
  否
  ↓
验证通过
  ↓
issues.md 标记为“已解决”
  ↓
将确认后的行为回写 bootstrap-spec.md
```

如果问题不是代码缺陷，而是用户改变了目标，先更新 `bootstrap-spec.md`；如果是技术方案变化，
更新 `plan.md`，再继续开发。不在 Bootstrap 阶段为了形式创建 SPEC、Change 或 Proposal。

## 是否需要按版本记录

Bootstrap 阶段不需要像正式版本一样维护完整的 V1.1、V1.2 变更体系，但建议给问题记录
标注发现阶段或检查点，例如 `Bootstrap`、`Checkpoint-01`、`Pre-V1`。这样可以知道：

- 问题是在什么阶段发现的；
- 哪些问题已经修复；
- 哪些问题被推迟；
- 哪些问题在后续版本基线前仍然存在。

不必为每次测试建立一个正式版本。只有形成阶段性可运行成果时，才创建一个检查点。

## 退出 Bootstrap

满足下面的退出清单后，再退出 Bootstrap：

- 核心功能可以运行；
- 主要架构和模块边界基本稳定；
- 阻塞问题已经处理；
- 未解决问题已经明确延期或接受风险；
- 用户确认建立 V1 基线。

如果 Bootstrap 中出现完全独立的新能力，先把它记录为 `bootstrap-spec.md` 中的待确认目标；
用户确认范围后，若它已经值得单独验收，就结束 Bootstrap，转入首次开发主循环，而不是
无限扩张同一份 `bootstrap-spec.md`。

通过退出清单后执行一次基线整理：

1. 读取 `bootstrap-spec.md`、`plan.md`、源码、测试和 `issues.md`；
2. 反向整理当前系统实际具备的功能；
3. 生成 V1 的 `brief.md`、完整 `spec.md`、正式 `plan.md` 和 `acceptance.md`；
4. 将已知未修复问题和暂缓事项写入正式记录；
5. 形成 V1 版本基线；
6. 后续进入稳定版本变更模式。

反向生成的 SPEC 和正式 Plan 必须标注为“根据实际实现整理的 V1 基线文档”，不能假装
成项目最初就已经确定的需求。
