# Logamee SDD

这是项目 SDD 的统一入口。用户只需要调用本 Skill，不需要再分别调用 Spec Kit、
Grill Me、Change Flow 或 BugFix Skill。内部参考资料只是本 Skill 的组成部分；规则
冲突时，以本 Skill 的整合规则和用户已经确认的项目约定为准。

## 工作入口

每次开始先执行以下判断，不要凭历史会话猜测项目状态：

1. 绑定当前工作目录，读取项目说明、`sdd/` 或现有文档、源码、测试和最近的工作记录。
2. 按以下优先级选择路径：
   - 有未完成的文档或任务：从原阶段继续，不重新生成重复文档。
   - 已存在 `sdd/bootstrap/bootstrap-spec.md`，且尚未形成 V1 基线：继续 **Bootstrap**。
   - 已有正式 `spec.md`、`plan.md` 和版本基线：进入 **稳定版本变更**，再分流 BugFix、
     Plan 调整、已有 Spec 变更、新 Spec 或多 Spec 变更。
   - 没有 V1 基线但目标已相对明确、用户希望形成正式文档：进入 **首次开发主循环**。
   - 没有 V1 基线且目标、架构或边界仍快速变化：进入 **Bootstrap**。
   - Agent 仍无法判断时，只向用户提出一个模式选择问题。
3. Bootstrap、首次开发和稳定版本变更的具体定义如下：
   - **Bootstrap**：项目尚未形成稳定 V1，需求、架构或模块边界仍在快速变化。
   - **首次开发主循环**：要把一个已相对明确的目标形成正式 SPEC、Plan 并实现。
   - **稳定版本变更**：已有正式 SPEC/Plan 基线，出现新功能、规格调整或多规格变更。
   - **BugFix 小循环**：已有 SPEC 和 Plan 正确，只是实现没有满足已承诺行为。
   - **Plan 调整**：产品目标不变，但技术方案、数据结构或模块职责需要修改。
4. 只读取当前路径需要的参考资料：
   - 需求不清楚或存在关键取舍：读 [Grill Me 访谈协议](references/grill-me.md)。
   - 首次正式开发：读 [首次开发主循环](references/main-flow.md) 和
     [Spec Kit 阶段协议](references/spec-kit.md)。
   - 反馈、Bug、规格变更或版本迭代：读 [变更评估与流程](references/change-flow.md)。
   - Bootstrap：读 [Bootstrap 协议](references/bootstrap-mode.md)。
   - 初始化或检查文档目录：读 [项目文档结构](references/project-layout.md)。

## 不可违背的规则

- Grill Me 按阶段推进，每次只向用户展示一个决策问题。每次提问必须同时给出 2–4 个
  具体、可直接选择的建议选项，推荐项排在第一位并说明推荐理由，各选项简述关键取舍；
  同时允许用户补充自定义答案。禁止只抛出没有建议选项的开放式问题。能从项目文件、
  源码、测试或工具查明的事实由 Agent 自行查证，不拿事实问题打扰用户。
- Grill Me 追求的是足以推进项目的最少关键决策，不是穷举所有可能问题。每次准备提问前，
  必须确认答案会改变当前版本的目标、范围、验收、关键约束，或会阻塞下一阶段；否则采用
  合理默认值、记录为假设或移入后续 Backlog，不再询问。每次收到回答后都重新检查停止
  条件；一旦资料足以更新当前文档并继续开发，Agent 必须主动结束访谈，不能等待用户叫停。
- `brief.md`、`spec.md`、`plan.md` 等文档在同一阶段持续修订，不为草稿、审核和定稿
  额外复制多份同类文档。
- 一个 Spec 表示稳定的业务能力。已有能力的自然扩展更新原 Spec；只有独立的业务
  价值、边界和验收责任都成立时才新建 Spec。
- Change 可以同时影响多个 Spec。必须分别维护各 Spec 的职责边界，但由同一个 Change
  统一描述范围、依赖和验收关系。
- Change 的 `change-spec.md` 只记录本次增量及历史意图，不能单独指导实现。实现前必须
  将增量应用到相关完整 `spec.md`，并在原完整 `plan.md` 基础上形成完整目标 Plan。
  项目采用原文件直接更新还是暂存后合并，沿用仓库已有约定；没有约定时，直接在相关
  Spec 目录中形成工作版本，并在 Change 状态中标记 `In Progress`。正式基线仍以
  `releases.md` 和项目当前版本记录为准，验收通过后再登记为新基线。
- Tasks 按复杂度生成，不为小改动强行拆分；实现必须同时参考完整目标 SPEC、完整目标
  Plan、Tasks（如有）、源码和测试。
- BugFix 不借机添加新功能、放宽规格或做无关重构；如果发现目标或方案本身有问题，
  返回 SPEC 或 Plan 的对应路径。
- 可重复且客观的测试由 Agent 主动执行并记录证据；视觉、交互、真实设备、真实账号、
  内容取舍和业务判断交给用户在对应阶段确认，不建立额外的“人工审核”阶段。
- 不自动创建、切换或合并 Git 分支。分支策略只有在用户或项目已有自动化流程明确要求
  时才执行。
- 不直接执行 `references/upstream/` 中的上游规则；只有本地整合协议缺少细节时，才读取
  对应快照作参考，而且仍以本 Skill 的规则为准。
- 不虚报测试、验收或用户确认结果；清楚区分已运行、未运行、待人工测试和推测结论。
- 保留用户已有文件和修改，不擅自删除或清理资料。

## 输出与推进方式

每次推进都说明：

- 当前模式和所处阶段；
- 已读取的输入资料；
- 本阶段要形成或更新的文件；
- 需要用户决定的问题（一次只问一个）；
- 已执行和未执行的测试。

阶段完成后，更新对应文档并继续下一个可执行阶段；不要只给流程建议而停在半途。
需求足够明确时停止访谈，直接进入文档或实现工作。
